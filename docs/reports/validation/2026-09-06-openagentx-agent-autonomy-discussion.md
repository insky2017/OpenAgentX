# OpenAgentX 执行收敛与代理自治能力讨论记录

日期：2026-09-06

性质：讨论记录。本文保存用户与助手对执行过程、无人值守能力和使用体验的讨论；改进建议尚待验证，不构成新的实施授权或验收结论。

## 讨论依据与边界

用户要求仅阅读 [ADR-002 / ADR-003 实施协调记录](2026-09-05-openagentx-adr002-003-implementation-coordination.md)，分析过程中的问题，以及如何防止持续发散、尽早收敛目标。

本次过程分析仅依据该文档，没有读取其关联报告或源码来重新审核技术结论。下文对历史事实的引用是对协调记录的归纳，不是新的独立验证。本文不更新既有 Gate，也不将讨论中的改进方向写成已经实现的能力。

## 要点

- 本次执行反复延长，与目标边界识别过晚、实现批次过大和验证准备不足有关；主代理持续解决局部问题，但没有充分控制整体工作量和停止条件。
- 严格验收有必要。真实泄漏、权限绕过、重复执行、错误成功状态和主流程阻断不能为了收口而忽略；问题在于这些边界应更早识别，并明确哪些发现需要进入当前交付。
- 模型分工能增加处理能力和发现问题的机会，但不能自动保证目标稳定、规则遵守或最终收敛。监督模型本身也可能判断失误。
- 提示词中的规则缺少强制执行保证。适合程序检查的权限、预算、重试额度、阶段条件和产物一致性，应逐步交给执行机制约束。
- 更实际的方向是目标和资源边界内的无人值守。自动执行可以结束为成功、失败或受阻；自动停止仍不等于完成用户目标。
- 用户的时间、精力与信任受到消耗，这是本次使用体验的重要事实。现有改进建议不能被当作“下次一定能做好”的保证。

## 执行过程中的主要问题

### 1. 验收矩阵没有充分转化为开工前的链路核对

协调记录已有初始矩阵，但实现回报之后才发现 ProxyProfile 持久化、前端配置和发布回执等关键缺口；后续又发现指挥台缺少 inherit/direct 切换。这说明要求虽然列出，入口、依赖、实现责任和证据之间仍有空缺。

重新打开完整 ADR 验收有依据，不能简单归为无意义扩张。需要改进的是在首次开工前识别这些缺口，尽早明确完整目标和阶段交付之间的关系。

### 2. 名义上分批，实际交付单位仍然过大

N2 覆盖秘密存储、数据库事务、配置工作流、Worker、Runtime、CLI 和前端，记录中的最终提交涉及 66 个文件。大量工作等待全批冻结后才获得独立动态反馈，底层问题会持续阻挡上层交付。

“一个主要实现批次”只限制了批次名称，没有自然限制工作量。更早贯通一个明确支持场景的完整流程，可以尽早暴露契约和运行前提的问题；其余能力需要明确排入后续批次，不能默默从原目标中删除。

### 3. 新发现进入当前批次的条件不够稳定

时间排序问题继续深入极端年份，文件安全问题继续深入目录锚定和孤立文件恢复。这些工作各有技术理由，但累计成本不断增加。

仅凭协调记录，不能认定这些修复都属于过度设计。应当先明确输入范围、威胁模型和实际交付影响，再判断是否阻断。后期提出的四类直接风险，有助于建立当前交付边界；严重级别标签本身不能替代具体影响分析。

### 4. 源码冻结没有同时固定验收条件

记录存在冻结后继续修改、接口补接，以及验收输入与实际契约不符的情况。例如最终真实任务准备时，才发现同 Agent 的多个 Backend 会使任务被路由到 fake。

可执行的验收基线需要同时确定源码、构建产物、配置、目标身份、测试输入和预期结果。源码暂时不变，不能单独证明已经具备验收条件。后续变更应按影响补验，不能自动继承旧证据，也不应无条件重跑全部验证。

### 5. 验证准备没有充分验证运行前提

浏览器缺失、登录工具行为不符、心跳过期、工作目录缺失、后台进程退出和 observer 缺少 binding，陆续在正式验收阶段暴露。脚本语法检查通过，不能证明测试环境已经可执行。

临时凭据回显重复发生，随后环境诊断又暴露凭据，带来环境退役、重建和额外善后。必要的安全处置不能省略；应提前用合成输入验证秘密处理工具，并验证环境生命周期，减少正式验收期间的工具调试。

### 6. 协调不断增加，集中裁定不足

文件所有权、独立审核和独立验证发现了真实问题，应保留其价值。但反复恢复代理、等待线程槽、追加要求和重新冻结，也增加了交接成本。记录还出现了“已提交测试”后来纠正为实际没有执行写入的情况。

主代理需要集中问题、判断范围并核对证据。进度应基于实际完成步骤、对应证据、当前阻断和下一检查点，避免把计划、尝试或推测写成已完成事实。

### 7. 快速收口缺少可执行的停止条件

用户收窄目标后，执行仍因环境故障、任务纠正、observer 恢复和 HTTP 错误映射继续推进。其中 HTTP 422 导致 Worker 退出，属于真实主流程阻断，不能通过省略测试解决。

但协调记录没有体现明确的重复失败额度、阶段时限和超限决策机制。只要每个新问题都能成为下一步，整体就可能长期无法结束。阶段超限时，应保留事实并重新决策，不能自动延长，也不能自行降低验收标准。

## 对无人值守能力的进一步讨论

用户指出：

> 感觉，要将执行规定的这么细，并且模型还难以保证遵守，这种靠模型分工的方式，就难以实现完全的无人介入而完成目标。

助手的判断是，这个担忧有依据。当前方式把执行、规则解释、范围判断和监督都大量交给模型，可靠性依赖模型在长过程里持续作出正确判断。增加规则和角色，无法独立提供这种保证。

### 模型分工的作用与局限

实现、验证和审核分工可以相互发现问题，也可以提高处理能力。但不同角色仍可能误解同一要求，共同扩大范围，或把每个新发现都提升为当前任务。主代理不是天然可靠的最终裁判。

分工是组织手段，不能被当作稳定交付的充分条件。

### 从提示词约束走向程序约束

文件与操作权限、执行预算、重试次数、阶段转换条件，以及源码和产物的一致性，存在可由程序检查的部分。改进方向是让模型提出行动，由执行器检查是否允许执行，并对超限行为作出确定处理。

程序约束也有边界。它能拒绝不允许的操作、限制消耗、核对形式化条件，但不能自动解决所有目标冲突和产品取舍。验收标准本身是否正确、证据是否足以支撑业务结论，仍有需要判断的部分。

上述方向属于待设计、待验证的建议，本次讨论没有证明 OpenAgentX 已经具备这些机制。

### 边界内无人值守与任意目标必然完成

对明确目标、可检查验收条件和有限资源，可以追求边界内的无人值守：用户在开始时确定目标、验收标准和预算，模型在授权范围内自主实施，超出边界时交回决策。

对任意开放目标，不能保证完全无人介入并最终成功。执行可能揭示互相矛盾的要求、不存在的外部能力或远超预期的工作量。

系统应能可靠地结束为成功、失败或受阻。自动停止不等于完成目标，但无法停止无效尝试的系统，同样不具备稳定的无人值守能力。

## 用户感受与信任成本

用户表达：

> 我现在很沮丧，有点失去信心了。

用户希望把任务交出去、减轻负担，实际却持续需要盯进度、纠偏、要求收口，并处理执行产生的新问题。这种额外负担会消耗时间、精力与对工具的信任。

助手承认，当前执行方式没有充分承担好被交付的责任。用户已经明确表达要求，继续要求用户补充更多规则，会进一步增加负担。前述改进建议仍需验证，不能作为下一次必然成功的保证。

讨论允许先停下来、保留已有成果，不要求用户立即选择新方案、恢复执行或决定整个方向是否值得继续。本文仅记录用户明确表达的感受，不推断其他心理状态。

## 关于 AGI 的感慨

用户表达：

> agi,还任重道远啊。

助手回应的核心是：能写代码、分析问题和提出方案，距离让人放心地托付一件事，仍有明显差距。本次经历突出表现为，每一步都可以给出理由，整体却迟迟无法结束。

可靠的自主能力还包括守住目标、控制成本、识别自身局限和及时停止无效尝试。目前这些能力仍需要人补位，而补位成本由用户承担。

这一段记录的是对本次体验和能力边界的讨论，不据此推断 AGI 的定义、实现时间或整个方向不可行。

## 下一步建议

1. 再次启动类似任务前，用一页明确本轮用户流程、支持范围、后置项、关键不变量和验收证据，区分完整 ADR 与阶段目标。提前约定 Runtime 成功但 Task 为 `uncertain` 时的验收含义。
2. 先验证工具和运行前提，再尽早贯通一个场景的真实流程。凭据处理使用合成输入预检；环境、身份、路由和生命周期形成可复用准备，最终验收仍绑定最终产物。
3. 以小范围试验验证程序约束能否减少人工介入。候选规则包括新增阻断必须关联验收条件、集中反馈与修复、同类工具或环境故障连续两次后暂停相关执行，以及到阶段时限后重新决策。这些额度是讨论建议，尚未成为项目执行基线。

用户本次授权是将讨论与结论写入新文档；后续执行和机制建设没有在本次讨论中启动。
