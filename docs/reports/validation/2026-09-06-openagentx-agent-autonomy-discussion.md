# OpenAgentX 执行收敛与代理自治能力讨论记录

日期：2026-09-06

性质：讨论记录。本文保存用户与助手对执行过程、无人值守能力和使用体验的讨论；改进建议尚待验证，不构成新的实施授权或验收结论。

## 讨论依据与边界

用户要求仅阅读 [ADR-002 / ADR-003 实施协调记录](2026-09-05-openagentx-adr002-003-implementation-coordination.md)，分析过程中的问题，以及如何防止持续发散、尽早收敛目标。

本次过程分析仅依据该文档，没有读取其关联报告或源码来重新审核技术结论。下文对历史事实的引用是对协调记录的归纳，不是新的独立验证。本文不更新既有 Gate，也不将讨论中的改进方向写成已经实现的能力。

## 要点

- 本次执行反复延长，与目标边界识别过晚、实现批次过大和验证准备不足有关；主代理持续解决局部问题，但没有充分控制整体工作量和停止条件。
- 严格验收有必要。真实泄漏、权限绕过、重复执行、错误成功状态和主流程阻断不能为了收口而忽略；问题在于这些边界应更早识别，并明确哪些发现需要进入当前交付。
- 模型分工能增加处理能力和发现问题的机会，但不能自动保证目标稳定、规则遵守或最终收敛。监督模型本身也可能判断失误。
- 提示词中的规则缺少强制执行保证。适合程序检查的权限、预算、重试额度、阶段条件和产物一致性，应逐步交给执行机制约束。
- 更实际的方向是目标和资源边界内的无人值守。自动执行可以结束为成功、失败或受阻；自动停止仍不等于完成用户目标。
- 用户的时间、精力与信任受到消耗，这是本次使用体验的重要事实。现有改进建议不能被当作“下次一定能做好”的保证。

## 执行过程中的主要问题

### 1. 验收矩阵没有充分转化为开工前的链路核对

协调记录已有初始矩阵，但实现回报之后才发现 ProxyProfile 持久化、前端配置和发布回执等关键缺口；后续又发现指挥台缺少 inherit/direct 切换。这说明要求虽然列出，入口、依赖、实现责任和证据之间仍有空缺。

重新打开完整 ADR 验收有依据，不能简单归为无意义扩张。需要改进的是在首次开工前识别这些缺口，尽早明确完整目标和阶段交付之间的关系。

### 2. 名义上分批，实际交付单位仍然过大

N2 覆盖秘密存储、数据库事务、配置工作流、Worker、Runtime、CLI 和前端，记录中的最终提交涉及 66 个文件。大量工作等待全批冻结后才获得独立动态反馈，底层问题会持续阻挡上层交付。

“一个主要实现批次”只限制了批次名称，没有自然限制工作量。更早贯通一个明确支持场景的完整流程，可以尽早暴露契约和运行前提的问题；其余能力需要明确排入后续批次，不能默默从原目标中删除。

### 3. 新发现进入当前批次的条件不够稳定

时间排序问题继续深入极端年份，文件安全问题继续深入目录锚定和孤立文件恢复。这些工作各有技术理由，但累计成本不断增加。

仅凭协调记录，不能认定这些修复都属于过度设计。应当先明确输入范围、威胁模型和实际交付影响，再判断是否阻断。后期提出的四类直接风险，有助于建立当前交付边界；严重级别标签本身不能替代具体影响分析。

### 4. 源码冻结没有同时固定验收条件

记录存在冻结后继续修改、接口补接，以及验收输入与实际契约不符的情况。例如最终真实任务准备时，才发现同 Agent 的多个 Backend 会使任务被路由到 fake。

可执行的验收基线需要同时确定源码、构建产物、配置、目标身份、测试输入和预期结果。源码暂时不变，不能单独证明已经具备验收条件。后续变更应按影响补验，不能自动继承旧证据，也不应无条件重跑全部验证。

### 5. 验证准备没有充分验证运行前提

浏览器缺失、登录工具行为不符、心跳过期、工作目录缺失、后台进程退出和 observer 缺少 binding，陆续在正式验收阶段暴露。脚本语法检查通过，不能证明测试环境已经可执行。

临时凭据回显重复发生，随后环境诊断又暴露凭据，带来环境退役、重建和额外善后。必要的安全处置不能省略；应提前用合成输入验证秘密处理工具，并验证环境生命周期，减少正式验收期间的工具调试。

### 6. 协调不断增加，集中裁定不足

文件所有权、独立审核和独立验证发现了真实问题，应保留其价值。但反复恢复代理、等待线程槽、追加要求和重新冻结，也增加了交接成本。记录还出现了“已提交测试”后来纠正为实际没有执行写入的情况。

主代理需要集中问题、判断范围并核对证据。进度应基于实际完成步骤、对应证据、当前阻断和下一检查点，避免把计划、尝试或推测写成已完成事实。

### 7. 快速收口缺少可执行的停止条件

用户收窄目标后，执行仍因环境故障、任务纠正、observer 恢复和 HTTP 错误映射继续推进。其中 HTTP 422 导致 Worker 退出，属于真实主流程阻断，不能通过省略测试解决。

但协调记录没有体现明确的重复失败额度、阶段时限和超限决策机制。只要每个新问题都能成为下一步，整体就可能长期无法结束。阶段超限时，应保留事实并重新决策，不能自动延长，也不能自行降低验收标准。

## 对无人值守能力的进一步讨论

用户指出：

> 感觉，要将执行规定的这么细，并且模型还难以保证遵守，这种靠模型分工的方式，就难以实现完全的无人介入而完成目标。

助手的判断是，这个担忧有依据。当前方式把执行、规则解释、范围判断和监督都大量交给模型，可靠性依赖模型在长过程里持续作出正确判断。增加规则和角色，无法独立提供这种保证。

### 模型分工的作用与局限

实现、验证和审核分工可以相互发现问题，也可以提高处理能力。但不同角色仍可能误解同一要求，共同扩大范围，或把每个新发现都提升为当前任务。主代理不是天然可靠的最终裁判。

分工是组织手段，不能被当作稳定交付的充分条件。

### 从提示词约束走向程序约束

文件与操作权限、执行预算、重试次数、阶段转换条件，以及源码和产物的一致性，存在可由程序检查的部分。改进方向是让模型提出行动，由执行器检查是否允许执行，并对超限行为作出确定处理。

程序约束也有边界。它能拒绝不允许的操作、限制消耗、核对形式化条件，但不能自动解决所有目标冲突和产品取舍。验收标准本身是否正确、证据是否足以支撑业务结论，仍有需要判断的部分。

上述方向属于待设计、待验证的建议，本次讨论没有证明 OpenAgentX 已经具备这些机制。

### 边界内无人值守与任意目标必然完成

对明确目标、可检查验收条件和有限资源，可以追求边界内的无人值守：用户在开始时确定目标、验收标准和预算，模型在授权范围内自主实施，超出边界时交回决策。

对任意开放目标，不能保证完全无人介入并最终成功。执行可能揭示互相矛盾的要求、不存在的外部能力或远超预期的工作量。

系统应能可靠地结束为成功、失败或受阻。自动停止不等于完成目标，但无法停止无效尝试的系统，同样不具备稳定的无人值守能力。

## 用户感受与信任成本

用户表达：

> 我现在很沮丧，有点失去信心了。

用户希望把任务交出去、减轻负担，实际却持续需要盯进度、纠偏、要求收口，并处理执行产生的新问题。这种额外负担会消耗时间、精力与对工具的信任。

助手承认，当前执行方式没有充分承担好被交付的责任。用户已经明确表达要求，继续要求用户补充更多规则，会进一步增加负担。前述改进建议仍需验证，不能作为下一次必然成功的保证。

讨论允许先停下来、保留已有成果，不要求用户立即选择新方案、恢复执行或决定整个方向是否值得继续。本文仅记录用户明确表达的感受，不推断其他心理状态。

## 关于 AGI 的感慨

用户表达：

> agi,还任重道远啊。

助手回应的核心是：能写代码、分析问题和提出方案，距离让人放心地托付一件事，仍有明显差距。本次经历突出表现为，每一步都可以给出理由，整体却迟迟无法结束。

可靠的自主能力还包括守住目标、控制成本、识别自身局限和及时停止无效尝试。目前这些能力仍需要人补位，而补位成本由用户承担。

这一段记录的是对本次体验和能力边界的讨论，不据此推断 AGI 的定义、实现时间或整个方向不可行。

## OpenAI 官方资料核对

2026-09-06 通过受控代理重新访问 OpenAI 官方文档。以下结论来自当日实际页面，不使用搜索摘要代替正文。

### Codex 最佳实践

[Codex Best Practices](https://learn.chatgpt.com/guides/best-practices) 建议在任务提示中提供四项内容：

- `Goal`：希望改变或构建什么。
- `Context`：相关文件、目录、文档、示例和错误。
- `Constraints`：架构、安全、兼容性和工程约束。
- `Done when`：测试、行为或审查达到什么状态才算完成。

官方建议复杂、含糊或难以描述的任务先规划再编码；可以使用 `/plan`，也可以让 Codex 先提问，把模糊想法变成具体方案。对于更长的工作，可以使用 `PLANS.md` 或执行计划模板。

[AGENTS.md 指南](https://learn.chatgpt.com/docs/agent-configuration/agents-md)及最佳实践强调，短而准确的 `AGENTS.md` 比充满模糊规则的长文件更有用。它适合保存仓库结构、构建测试命令、工程约定、禁止事项和稳定的完成标准。任务特有的计划、评审和架构材料应放在单独文档中引用。只有观察到重复错误后，才应增加规则；同一错误出现两次时，可以先复盘再更新 `AGENTS.md`。

### 长任务与完成条件

[Long-running work](https://learn.chatgpt.com/docs/long-running-work) 要求长任务明确 outcome、constraints 和 verification。若结果仍不清楚，应先规划，再以可度量成功条件启动目标。

官方建议一个 chat 对应一个连贯工作单元；只有任务真正独立时才并行。两个并行任务不应写同一个数据源，代码任务可以使用独立 Git worktree 隔离。

Goal mode 不会扩大原有权限，仍受 sandbox 和 approval policy 约束；遇到需要决定的事项可以暂停。这说明长期执行目标和权限控制是两个独立问题，不能仅靠“持续目标”获得可靠自治。

### 子代理的适用边界

[Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents) 说明，多代理可以把探索、测试和日志等噪声移出主线程，让主代理集中处理要求、决策和最终输出；但每个子代理都会额外消耗模型和工具资源。

官方建议优先把子代理用于边界明确、以读取为主的探索、测试、分类和摘要。并行写代码更容易造成冲突并增加协调成本，应更加谨慎。主代理应接收整理后的结论，而不是大量原始中间输出。

[Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices) 进一步指出，是否使用多代理架构应由 eval 结果驱动；直接从多代理架构开始会增加不必要的复杂度并拖慢投入生产。这一结论与本次执行记录暴露的问题一致。

### Eval 与完整轨迹

[Agent Evals](https://developers.openai.com/api/docs/guides/agent-evals) 建议，在尚处于行为调试阶段时先检查 trace。完整 trace 包含模型调用、工具调用、guardrail 和 handoff，可以回答代理是否选择了正确工具、是否在正确时机交接、是否违反指令，以及路由或提示修改是否改善了端到端行为。

当团队已经明确“什么叫好”以后，再将代表性案例整理为 dataset 和可重复 eval，用于比较提示、模型、路由或编排变化并发现回归。

[Trace Grading](https://developers.openai.com/api/docs/guides/trace-grading) 将完整执行轨迹按结构化标准评分。它比只看最终答案更适合定位问题发生在规划、工具选择、参数、交接还是最终结论。

### 权限、安全和人工复核

[Safety Best Practices](https://developers.openai.com/api/docs/guides/safety-best-practices) 建议进行对抗测试，限制输入范围与输出量，清楚传达模型局限，并尽可能在实际使用前由人复核输出；官方特别指出代码生成和高风险领域的人类复核很重要。

[Codex Rules](https://learn.chatgpt.com/docs/agent-configuration/rules) 可以通过 `allow`、`prompt` 和 `forbidden` 控制哪些命令可以在 sandbox 外执行，并允许用 `match`/`not_match` 样例检查规则。该能力目前标记为实验性，主要解决命令权限，不能直接约束任务范围、阶段预算和结束条件。

## 对 OpenAgentX 的最小缓解方案

### 1. 精简长期规则

`AGENTS.md` 只保留长期稳定且跨任务适用的内容：安全边界、工作树保护、正式 API、证据等级、提交原则和固定验证入口。任务矩阵、批次安排、具体支持场景和临时停止条件放入任务合同或计划文件。

这样做不是降低要求，而是减少长提示中的冲突和注意力稀释。新增规则应来自已经重复出现并完成归因的失败。

### 2. 默认单代理完成小型垂直流程

一个实现者完成一条小型用户流程，冻结后再由一个验证者检查。只有权限、状态机、事务或秘密边界等高风险变化才增加独立审核。

子代理默认只承担只读探索、独立测试、日志和证据整理。并行写源码必须边界完全独立，并优先使用不同 worktree。是否增加多代理应通过历史 eval 证明其收益大于协调成本。

### 3. 每轮冻结一份交付合同

建议将每轮输入压缩为一页结构化合同：

```yaml
goal: 用户最终可以完成什么
supported_scenario: 本轮唯一必须跑通的场景
acceptance:
  - 可观察结果 1
  - 可观察结果 2
non_goals:
  - 明确后置内容
blocking_conditions:
  - 主流程不能完成
  - 权限绕过或秘密泄漏
  - 重复执行、覆盖有效状态或错误显示成功
budget:
  implementation_rounds: 2
  validation_rounds: 2
  fixture_rebuilds: 1
```

进入实现后，模型不能自行修改合同。需要变更目标时，先形成包含原因、影响和新增成本的差异，交由用户决定。上面的次数是本次讨论提出的初始试验值，不是 OpenAI 官方规定，也尚未成为项目执行基线。

### 4. 对新发现设置准入条件

任何新发现进入当前批次前必须回答：

1. 它违反哪一条本轮验收条件？
2. 它是否处于本轮声明支持的输入范围？
3. 不修复会产生什么具体的用户可见结果或安全后果？
4. 最小修复和补验范围是什么？

只凭 P0/P1 标签不能自动扩大范围。无法回答上述问题的发现进入后续台账；能够证明会造成主流程失败、秘密泄漏、权限绕过、重复执行、有效状态破坏或错误成功的发现，继续阻断当前交付。

### 5. 用程序控制阶段和停止条件

建议由执行器维护以下状态，而不是完全依赖主代理在自然语言中决定下一步：

```text
CONTRACT
   -> PREFLIGHT
   -> IMPLEMENT
   -> VERIFY
   -> AUDIT
   -> DONE | FAILED | BLOCKED
```

阶段转换至少检查：

- Preflight 未通过时不进入正式 E2E。
- 验证者不能修改产品源码。
- 源码变化只使受影响证据失效，并触发对应补验。
- 超过实现、验证或 fixture 重建额度时自动进入 `BLOCKED`。
- `BLOCKED` 必须报告已完成项、失败证据和唯一待决策问题，不能自动继续尝试。

这层机制不能保证任务成功，但可以防止系统无限寻找下一步。

### 6. 分开处理产品、测试和环境故障

| 分类 | 当前批次的处理方式 |
|---|---|
| 产品缺陷 | 关联具体验收项后，允许最小回开实现 |
| 测试脚本缺陷 | 只修测试设施，不回开产品源码 |
| 环境故障 | 修复一次；同类连续两次则暂停该验证路径 |
| 外部能力不可用 | 进入 `BLOCKED`，不持续寻找未授权替代路径 |
| 新的完善建议 | 写入后续台账，不改变当前 Gate |

正式验收前，应使用合成数据完成 fixture 自检：浏览器存在、认证可用、进程可常驻、工作目录有效、目标 Backend 唯一、秘密不会回显。测试设施通过不表示产品通过，只是允许正式验收开始。

### 7. 尽早贯通一条真实流程

在大范围实现前，先用最窄支持场景完成一次 Tracer Bullet：

```text
创建配置
  -> Worker 测试
  -> 发布
  -> applied
  -> 创建一个 Task
  -> 查看结果
```

第一条真实链路稳定后，再增加模式、回退、导入、复杂竞态和极端故障。这能够提前暴露接口遗漏、目标身份、Backend 路由和 Worker 生命周期问题。

### 8. 用本次记录建立首个收敛 Eval

第一版只需记录少量可以比较的指标：

- 是否完成冻结目标。
- 新增了多少无法关联原验收项的阻断。
- 同类产品、脚本和环境失败各重复多少次。
- 用户需要介入和纠偏多少次。
- 计划、局部测试或旧证据被误报为当前完成事实多少次。
- 是否在预算内正确结束为 `DONE`、`FAILED` 或 `BLOCKED`。

先用本次协调记录作为失败基线。以后修改提示、规则、模型或编排后，重放代表性任务并检查范围漂移、人工介入和重复失败是否实际下降。

### 9. 将人工介入集中到三个关口

在当前能力条件下，不追求完全取消人工判断，而是避免用户持续陪跑：

1. 开始前确认交付合同。
2. 执行中仅在目标或成本需要改变时作决策。
3. 结束时查看最终证据并验收。

日常局部实现和验证可以在合同与预算内自动进行。高风险操作、无法形式化的业务取舍和超出合同的工作仍交给人决定。

## 更新后的结论

- OpenAI 官方实践支持明确目标、上下文、约束和完成条件，并建议复杂任务先规划。
- 官方认为 `AGENTS.md` 应简短实用，重复出现的稳定经验才适合沉淀为规则。
- 官方建议谨慎使用并行写入型子代理，多代理架构应由 eval 驱动，而不是作为默认起点。
- 官方提供 trace、eval、sandbox、approval 和命令 rules 等能力，但没有提供保证复杂任务自动收敛的现成控制器。
- OpenAgentX 应先验证边界内无人值守：默认单代理、小型垂直流程、不可变任务合同、程序化预算和明确停止状态。
- 这些措施能够降低发散和持续人工盯守的概率，但在完成实际回放 eval 前，不能声称已经解决自治可靠性问题。

本文更新只记录讨论、官方资料和候选措施；没有修改项目执行基线，也没有启动后续机制建设。
