# OpenAgentX 综合评估摘要

整理日期：2026-10-02。本文汇总既有架构快照及 **2026-09-23 至 26 日评估**，作为原报告的阅读入口；未重新审计或验收，不判断历史缺陷此后是否修复。下文的实现判断均指当时评估基线。

后续行动：[AGY 工作流修复计划](../../plans/2026-10-02-agy-workflow-repair.md) · [端到端测试用例](../../plans/2026-10-02-agy-workflow-e2e.md)（2026-10-02 制定，尚未实施）。

## 核心结论

- **架构骨架清楚，用户流程没有闭合。** 控制面、持久任务、常驻 Worker、Runtime 的分工合理；但“能不能开始、现在等什么、是否完成、如何取消和继续”缺少跨模块一致的答案，用户因此处处需要绕路。
- **功能部分达成，尚不足以判定可靠日用。** 真实浏览器到 AGY、文件产出、同 Worker 连续执行已经贯通；两次执行的 Run 成功、文件独立核验正确，Task 却仍为 `uncertain`。执行能力已有基础，结果确认和后续操作仍有缺口。
- **过度设计与核心薄弱同时存在，适合局部重构。** 事务、幂等、Mailbox、Journal、lease/fencing 应保留；未接线的组织治理、多 Runtime 抽象和暴露给用户的内部阶段应收敛。现有证据不支持全盘重写、微服务化或另建通用工作流平台。
- **测试有投入，但未充分约束真实体验。** 单元测试通过，仍复现取消失败、显示旧结果和首连恢复等问题。后续应以完整用户旅程及失败恢复验收，不能用包测试全绿代替产品可用。
- **参考项目的价值在小机制。** Paseo 对改善日常交互最直接，Holon 对长期 Domain Agent 理念最贴近；其余项目补充角色输入、结果追溯、停止回执等做法。没有一个项目值得据此整套搬入。

架构主线：**Web / Console → daemon 控制面 → SQLite / Mailbox / Journal → 常驻 Worker → Runtime Adapter → 外部 Agent CLI**。tmux 承载界面，不负责业务调度。详见[架构说明](../../design/CURRENT_ARCHITECTURE.md)与[HTML 架构图](../../design/current-architecture.html)。

## 各模块：哪些值得保留，哪些优先补齐

| 模块及详细报告 | 做得较好 | 主要缺口与处置方向 |
|---|---|---|
| [01 控制面与状态](2026-09-23/01-control-plane-and-state.md) | 事务一致性、幂等、审计及入口认证已有基础 | 排队／待输入取消失败；取消后失联可能误报确定结果；组织授权未完整接入。优先统一取消与终态规则 |
| [02 Worker / Runtime](2026-09-23/02-worker-and-runtime.md) | 常驻执行、连续任务、执行权隔离真实成立 | 角色文件未确定注入，完成与追问脱节；CodeBuddy 有空成功／超时缺口，ACP 未装配。先做实已支持的执行链 |
| [03 Web / PWA](2026-09-23/03-web-and-pwa.md) | 基础任务操作、过程展示、移动布局及部分离线保护可用 | 最新结果选错、忙闲判断和首次连接恢复不可靠。统一就绪、最新结果及可用动作的展示规则 |
| [04 Console / Fleet](2026-09-23/04-console-fleet-and-onboarding.md) | 管理、TUI 与独立 Worker 生命周期有验证 | overview 空白、状态裁切、进入与返回绕路。补首次使用导航，降低操作与 tmux 布局的耦合 |
| [05 网络工作流](2026-09-23/05-network-workflow.md) | 配置版本、测试、发布、应用回执与代际约束较完整 | 前置条件隐蔽，配置探测不等于模型可调用。直接显示阻塞原因和恢复入口，内部版本按需展开 |
| [06 部署与可观测性](2026-09-23/06-deployment-and-observability.md) | 已核对安装来源、进程与文件哈希 | 主线、旁支、安装版本和文档入口分散。收敛安装／恢复指南，明确“开发、已安装、已验收”的区别 |

**`OAX:overview` 为什么空？** 评估确认它只是预留的 shell 窗口，没有总览渲染程序。建议最小内容为：Agent 是否就绪及原因、待输入／审批／核验的任务、最近结果、连接恢复和任务入口。先解决“进来后知道下一步做什么”。

## 八个参考项目：分别看什么

以下为固定版本源码研究与有限局部测试的归纳，不能视为八个项目都已通过真实模型、浏览器或业务 E2E。

| 项目及详细报告 | 最值得借鉴 | 借鉴边界 |
|---|---|---|
| [Paseo](2026-09-23/07-paseo-reference.md) | 发送、过程、结果、继续、停止组成连贯会话 | 会话空闲不等于业务成功；保留自己的持久任务记录 |
| [Multica](2026-09-23/08-multica-reference.md) | 角色指令真正送达执行端，任务与执行分层 | 不照搬自动审批／重跑；移植需注意额外商业及品牌许可条件 |
| [OpenHarness](2026-09-24/09-openharness-reference.md) | 明确消息投递的不确定性，按执行尝试保存结果 | 取消标记不等于停止确认，重试需考虑已有副作用 |
| [Wake](2026-09-24/10-wake-reference.md) | 历史检索、正文与继续入口使用一致的结果身份 | 定位是会话资料库，不能承担任务执行和调度 |
| [Orca](2026-09-25/11-orca-reference.md) | 明确执行归属、用户操作及未确认停止状态 | 执行报告仍需核验，多入口与兼容层迁入成本较高 |
| [FenixAgent](2026-09-26/12-fenixagent-reference.md) | 按当前轮次统一处理回复、工具、审批与取消 | 部分定时执行路径会误报成功，不能照搬完成判据 |
| [Holon](2026-09-26-holon/13-holon-reference.md) | 稳定 Agent 负责一个领域，持有可恢复工作记录与交付责任 | Domain 职责不等于权限隔离；自有 Runtime 不宜直接替换现有底座 |
| [Buzz](2026-09-26-buzz/14-buzz-reference.md) | 分开身份、在线、管理权与停止回执，诚实表达未知 | 会话正常返回不等于业务完成，任务标识也不保证幂等 |

对“一个 Agent 一个 domain”的设想，建议保留**稳定身份、明确职责、实际生效的角色输入、可恢复的工作记录、等待与交付责任**。先让一个领域 Agent 可靠完成工作，再扩展跨领域委派；不要提前复制 Holon 或 Buzz 的整套运行平台。

## 下一步：按三个可验收结果推进

1. **先能撤回、能看准结果。** 修排队／待输入取消、失联后误报取消成功、最新回复选错。验收：撤回任务不再执行，停止未确认时保留未知，页面展示本次结果。
2. **再真正完成一项工作，并能继续。** 衔接 ADR-006 的问答／有副作用任务规则，落实角色注入及完成后的追问入口。验收：真实浏览器 → AGY → 问答或文件产物 → 结果核验 → 下一项，逐层检查 Task、Run 和实际效果。
3. **随后做到从零可用、故障可恢复。** 补 overview、就绪原因、网络引导、首次连接失败恢复与 Console 返回路径。验收从未预配的新用户环境开始，同时覆盖断线、移动端与小终端。

这三步是建议顺序，尚不代表修复已实施。启用 CodeBuddy 或开放多用户／组织权限前，其对应执行与授权缺口应先处理。完整根因、证据边界和分期依据见[原总体评估](2026-09-23/00-overall-assessment.md)。
