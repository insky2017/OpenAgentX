# Buzz 与 OpenAgentX 对照研究

## 结论

- **Buzz 的重心是人和 Agent 共用一个协作工作区。** 稳定身份、消息与代码/工作流记录有共同入口；这与 OpenAgentX 托管 CLI Runtime、交付可验证任务的控制面有交集，但目标规模不同。
- **对 OpenAgentX 最有价值的是用户动作后的状态契约。** 消息被接收、Agent 在线、某轮结束、停止已请求、业务效果已确认要分别表达；不能拿部署回执或一次发送成功代替实际结果。
- **借鉴能力与就绪原因的统一来源。** 工具是否安装、适配器是否可用、配置是否完整和运行是否健康不应只靠一个 online 标记。具体原因与恢复入口比增加配置页更有价值。
- **单次任务执行器比全平台更适合直接对照。** `buzz-acp run` 复用身份、角色和会话设置，但明确 `completed`/退出 0 只是回合正常返回，taskId 也不负责去重。OpenAgentX 应保留自己的持久任务账与业务效果核验。
- **功能广度不能直接证明完整交付。** 当前 Workflow 审批虽有 schema 和部分界面/API，执行收口仍明确返回 `approval_not_supported`；源码边界和本轮实测分别记录。
- **权限协议与人工审批需分开。** `buzz-acp` 收到工具权限请求会优先选择 `allow_once`，因此存在权限协议不代表用户逐次批准；角色、频道成员和宿主 shell 权限也不是同一边界。
- **暂不迁入整套协作基础设施。** Nostr 签名事件、Postgres/Redis、Git 托管、多端应用和远程部署针对 Buzz 的产品范围；目前 OAX 的取消、可信结果、角色输入和继续路径不足以支持一次平台替换。

## 与长期 Domain Agent 的关系

Holon 侧重长期 Agent 的工作项、记忆和等待恢复；Buzz 侧重同一社区中人和 Agent 的沟通、共享材料与执行入口。OpenAgentX 可以保留“一个领域有稳定负责人”，先用既有 Agent、Task、RunAttempt、SessionBinding 和 Journal 明确职责输入与交付归属。社区、频道或角色名称不能自动成为 OS 隔离或业务验收边界。
