7: **Agents that act and follow through**
8: 
9: Holon is a local workbench for agents handling ongoing work—not just one-off prompts. It keeps goals, plans, progress, and wait conditions in explicit WorkItems, so work can continue across sessions, commands, human input, and external events.
10: 
11: When the next condition is satisfied, the agent resumes the right work in the right workspace and delivers the result back to you.
12: 
13: Use Holon when a task should keep moving after you close the terminal, wait for a command result, ask for review, or receive an external event.
14: 
15: Holon itself is not an agent. It provides a local working environment for multiple agents. Agents understand goals and drive execution; Holon treats "work" as the core unit, preserving state, organizing context, recording waits and wakes, so tasks can resume at the right time and eventually deliver results back to the operator.
16: 
17: ## What does Holon provide?
18: 
19: | Capability | What it means |
20: |---|---|
21: | **Continuous agent workspace** | Each agent has its own continuous working context in Holon, instead of restarting with every terminal, request, or client connection. |
22: | **Work-first task model** | Holon organizes tasks, waits, execution progress, and final delivery as explicit Work, instead of leaving them scattered across conversations. |
23: | **Event-driven wait and wake** | Agents can wait for task results, external events, or operator input, then return to the corresponding work when the condition is satisfied. |
24: | **Explicit context and trust boundaries** | Holon distinguishes operator input, external events, tool results, and internal execution traces so information from different origins is not mixed together. |
25: | **Local-first execution environment** | Holon is built for local repositories, shell, worktrees, and development toolchains, letting agents execute tasks in the real working environment. |

9: ## Summary
10: 
11: Holon should treat every agent as the same addressable runtime object.
12: 
13: `public agent` and `private agent` should no longer be product-level identity
14: classes. A subagent is an agent with explicit lineage, supervision, durability,
15: lifecycle attachment, and policy relations. It is not a hidden or lesser
16: runtime species.
17: 
18: The first agent-facing native tool surface should separate three operations
19: that are currently combined by `SpawnAgent` or hidden behind invocation:
20: 
21: 1. `CreateAgent` creates an independently managed agent identity.
22: 2. `SendAgentMessage` durably admits one asynchronous message to an existing
23:    authorized agent.
24: 3. `InvokeAgent` is a convenience operation: for `existing_agent` it sends a
25:    message and returns a message-arrival wait handle; for `new_subagent` it
26:    creates a supervised child and returns a result-bearing task handle.
27: 
28: The runtime uses one internal `AgentMessageDeliveryService` for
29: `SendAgentMessage`, existing-agent invocation, operator ingress, and future
30: protocol adapters. None of those surfaces may create a private queue path.
31: 
32: Every adapter must call the same application service. Native runtime tools must
33: not fork the CLI to implement runtime semantics.
34: 
35: Message delivery is not synchronous RPC. Acceptance means that Holon durably
36: admitted one message under an identity-lifecycle fence. It does not mean that a
37: turn completed or that the target produced a result. A message-arrival wait
38: handle means only that a later message from the selected agent reached the
39: caller's durable inbox boundary; it does not represent business completion.

85: ### Why different roles, rather than just multiple chat windows?
86: 
87: Having two agents discuss the same code does not establish collaboration. Who makes the changes? Who judges whether those changes address the issues? Who decides when opinions differ? Without these agreements, another round of conversation may just repeat the argument.
88: 
89: Roles first need to define decision boundaries. The familiar PR workflow makes this clear: the development agent submits changes and responds to issues; the reviewer checks risks and verification evidence and judges whether merging is appropriate within its authorization. Disputed or out-of-scope trade-offs go to you. The earlier example authorized conditional merging, not publishing a release. These agreements come from the responsibilities you assign, not from the name "reviewer."
90: 
91: Separate roles also let work advance independently. While a development agent fixes an interface, a documentation agent can check usage instructions that are already stable. If a change tightly couples the frontend and backend, though, one agent may handle it more directly. Dividing the work is not worth an unnecessary handoff.
92: 
93: Long-term roles also have experience worth keeping. A testing agent can maintain regression scenarios that are easy to miss. An operations agent can record log locations, diagnostic steps, and operations that need human confirmation. These materials need revision as work happens; they support repeated collaboration better than explaining responsibilities from scratch each time.
94: 
95: ### Keep roles and experience in AgentHome
96: 
97: Each agent has its own AgentHome to keep its responsibilities, memory, and materials. Its `AGENTS.md` can record the role contract: what it handles, what it can do directly, and what it must ask you to confirm. This file records existing authorization. Editing its text does not expand the agent's actual permissions.
98: 
99: Role agreements also differ from project rules. The reviewer's review responsibilities belong in its own AgentHome; how a repository builds and runs tests stays in the corresponding workspace. This lets it reuse its review methods in another project while following that project's specific requirements.
100: 
101: You can start from a template when creating a role. Reusable methods can become Skills, such as review steps, documentation checks, or log investigation. If you temporarily need an independent second look, you can delegate to a child agent and end that assignment after receiving the results, without maintaining a long-term role for every small task. For configuration, see the [Agent templates](/reference/agent-templates) and [Skills](/reference/skills) references (in English).
102: 
103: ### Keep unfinished work and continue when conditions allow
104: 
105: In Holon, the agent persists over the long term, while individual pieces of work have a starting point and acceptance conditions. A WorkItem is the record of such work: it saves the objective, plan, progress, waiting conditions, and final completion report.
106: 
107: With this record, "waiting for test results" and "delivered" are different states. The agent yields execution while waiting. When task results, operator input, or integrated external events arrive, the runtime schedules it to continue. The model does not need to keep looping to ask whether results are ready.
108: 
109: This fits reviews spanning multiple rounds of feedback, as well as documentation, investigation, and acceptance work with staged confirmation. Ordinary questions can still end directly; explaining a command does not require a full work item.
110: 
111: WorkItem does not guarantee infinite context or lossless recovery. Its records need ongoing maintenance so agents and people can check whether the objective has changed and whether the next step still makes sense. For what is saved and how waiting works, see [Holon's WorkItem architecture: separating work state from conversation](/blog/why-work-items).
112: 
113: ## Let agents work directly in your projects
114: 
115: Agents can directly use the repositories, shell, and toolchain on the machine running Holon. After connecting to an existing project, an agent follows project rules to edit files and run tests. After drafting documentation, it can build the site to check pages. You receive actual workspace changes and verification results that you can continue to edit, review, or commit.
116: 
117: One agent can bind multiple workspaces and switch between them. For example, adding an interface may require first changing the server, then updating the SDK, and finally adjusting the application that uses it. A development agent can work toward the same objective through each repository's changes and verification. Each project's code, build methods, and guidance files stay in its own directory. When changes need isolation, it can also create a separate Git worktree for the corresponding repository. See the [workspace reference](/reference/workspaces) (in English) for details.
118: 
119: Models and image tools can be configured for the work, for example to prepare illustrations for documentation or read page screenshots for inspection. When using remote models, requests still go to the corresponding services, so choose models and the material you send according to the project's data requirements. See the [model reference](/reference/models), [image understanding](/reference/view-image), and [image generation](/reference/image-generation) reference pages (in English) for supported capabilities and required credentials.
120: 
121: ## Teams share responsibilities and work results
122: 
123: Individuals can use Holon to organize their remote development environments. Teams can put shared roles on a server so members can hand off the same piece of work, rather than each person investigating from scratch. Role assignments do not replace system permissions or access controls. The deployer must still manage the server's network, credentials, and actual access scope.

13: ## The host-local runtime
14: 
15: Holon runs as a user-level process on your machine. It is **not a sandbox**:
16: 
17: - Agents can run any command your user account can run.
18: - File operations use your user permissions.
19: - Network access follows your host's network configuration.
20: - There is no container, VM, or seccomp isolation built into the runtime.
21: 
22: **What this means:** scope workspaces intentionally, use dedicated user
23: accounts or containers when running untrusted agent workloads, and treat agent
24: command execution with the same care you'd give a shell script running as your
25: user.
26: 
27: ## Execution environment summary
28: 
29: Every agent receives an execution environment summary in context. This summary
30: describes the current policy snapshot and what is enforced:
31: 
32: | Boundary | Level | What it means |
33: |----------|-------|---------------|
34: | `cwd_rooting` | runtime_shaped | The runtime allows workdir outside the workspace root when explicitly requested; sandboxing is the responsibility of the execution backend |
35: | `projection_rooting` | hard_enforced | Filesystem views are constrained to the projected root |
36: | `path_confinement` | not_enforced | The runtime does not prevent access outside the workspace by path |
37: | `write_confinement` | not_enforced | Write operations are not restricted to the workspace |
38: | `network_confinement` | not_enforced | Network access is unrestricted by default |
39: | `secret_isolation` | not_enforced | The runtime does not isolate secrets from agent commands |
40: | `child_process_containment` | not_enforced | Spawned child processes are not confined by the runtime |
41: 
42: **Key takeaway:** boundaries marked `hard_enforced` are runtime guarantees.
43: Boundaries marked `not_enforced` rely on the operator's host configuration
44: (filesystem permissions, firewall rules, container isolation).
45: 
46: ## Workspace binding
47: 
48: Holon provides workspace binding that constrains where the agent operates:
49: 
50: - **Workspace root** — the agent's default working directory. The runtime
51:   defaults commands to start inside this root, but an explicit workdir may
52:   point outside the workspace when the execution backend allows it.
53: - **Projection root** — constrains the filesystem view presented to the agent.
54:   When enforced, the agent only sees files under the projection root.
55: - **ApplyPatch targets** — file mutation tools resolve relative paths against
56:   the active workspace by default.
57: 
58: These bindings are **organizational guardrails**, not security boundaries:
59: an agent that can execute arbitrary shell commands can `cd /etc` or read files
60: outside the workspace if your OS permissions allow it. For true confinement,
61: pair Holon with a container, VM, or dedicated user account.

7: # RFC: Long-Lived Context Memory
8: 
9: ## Summary
10: 
11: Holon is designed around one durable agent with long-lived working memory.
12: The runtime should not require an operator-visible "new session" reset to keep
13: an agent useful.
14: 
15: This RFC covers cross-turn memory and prompt assembly. In-turn provider
16: conversation compaction inside one `run_agent_loop()` is handled separately by
17: `docs/rfcs/turn-local-context-compaction.md`.
18: 
19: This RFC defines the context compression and memory model that lets a Holon
20: agent continue across many turns while keeping prompt growth bounded.
21: 
22: The core design is:
23: 
24: - keep append-only durable logs as the audit source
25: - derive a deterministic working memory snapshot after turns
26: - accumulate active work into episode builders
27: - finalize immutable episode records at meaningful boundaries
28: - assemble each prompt from budgeted memory sections instead of replaying all
29:   history
30: - keep provider prompt-cache identity aligned with slow-changing memory
31:   revisions
32: 
33: This RFC uses "memory" in the runtime-continuity sense. Curated durable memory,
34: loaded guidance, runtime evidence, working-memory projection, and compaction
35: output remain separate governance surfaces; see

[policy-rfc] docs/rfcs/agent-identity-relations-and-message-delivery.md
https://github.com/holon-run/holon/blob/7c0ebbdfbf2f38adf41968051ed3440bc5ddb774/docs/rfcs/agent-identity-relations-and-message-delivery.md#L342
342: The initial send policy is:
343: 
344: | Caller evidence | Initial send decision |
345: |---|---|
346: | authenticated operator control with `agent.message.send` scope | allow unless an applicable explicit deny exists |
347: | active supervising parent using the supervision follow-up route | allow while that supervision remains active |
348: | lineage parent without active supervision | deny unless an explicit scoped allow exists |
349: | peer agent using the `agent_invocation` route to an active persistent independent target | allow unless an applicable explicit rule overrides it |
350: | any other peer-agent message | deny unless an explicit scoped allow exists |
351: | configured external ingress binding | allow only within that binding's target and content scope |
352: | any other caller | deny |
353: 
354: Lifecycle fences and authenticated namespace resolution run before policy
355: grants. Within message policy, an applicable explicit deny wins over derived or
356: explicit allow. A narrower principal, target, route, or ingress-binding rule
357: wins over a broader rule; equally scoped conflicting rules resolve to deny.
358: Operator control may change policy through a separate authorized management
359: operation, but message admission does not silently bypass an explicit deny.
