# Holon 与 Domain Agent 对照研究

## 结论

- **长期职责这一点接近。** Holon 为每个 Agent 保存身份、队列、状态、上下文和工作现场，已有 Agent 间可以发送消息，也可以创建受监督的子 Agent。把某个 Agent 长期指定为一个业务领域的负责人，是这种机制能够承载的使用方式。
- **一个 Agent 一个 domain 不是自动成立的强约束。** 职责描述、运行时能力、消息准入和 OS 隔离是不同层次；领域名称或 workspace 绑定不能自动变成所有资源的权限边界。是否存在唯一负责人、允许调用哪些其他领域、结果由谁验收，要看具体契约。
- **两者处在不同架构层次。** Holon 自己实现 Provider、工具循环、工作项和等待唤醒；OpenAgentX 用控制面和常驻 Worker 托管 CLI Runtime。可以借鉴长期职责、交付和观察模型，不能把替换 runtime 当成一次小型 UI 重构。
- **值得借鉴的是工作责任与交付分开建模。** WorkItem 表达持续目标，Task 表达一次受监督执行，brief 表达操作者可见交付；peer 消息被接收、收到对方消息、子任务结束与目标完成分别判断。OpenAgentX 已有 Task/RunAttempt/Journal，应先补清楚对应语义。
- **完成与隔离仍有边界。** Holon 要求完成报告、执行归属和状态条件，这有助于避免“模型停了就是成功”；报告本身仍不等于业务效果独立核验。其运行时、身份迁移与上下文系统也较复杂，不能据理念相近断言整体更可靠或更简单。

## 对一个 Agent 一个 domain 的判断

后续追加：[Buzz 研究与八项目对照](../2026-09-26-buzz/README.md)。本批保留 Holon 的固定版本和独立测试结论。

这个方向可以保留，建议明确为“一个领域有稳定的职责负责人”。职责负责人可以处理多项工作，也可以委派有界子任务；是否允许多个负责人、共享资源或更换执行器，是另外的产品决策。

| 需要说清的契约 | Holon 提供的参考 | OpenAgentX 当前最小落点 |
|---|---|---|
| 长期负责什么 | Agent 身份、AGENTS.md、工作区与记忆 | 用稳定 agent_id 和现有角色配置表达职责，并验证指令实际进入 Runtime；暂不因术语相似新建 Domain 平台 |
| 可以影响什么 | capability family、消息准入与执行边界分开 | 沿用现有身份、授权和 Worker 约束；不能把职责说明当作硬权限，也不能把未接线的组织策略算已生效 |
| 别人交来的工作如何收口 | 持久消息回执、peer message wait、受监督 child Task 各有不同结果 | 先贯通一次关联请求→执行→结果→发起方验收；回复到达不等于完成业务，未知效果不自动重发 |
| 用户从哪里接手 | brief 与内部 trace 分开，显式等待/阻塞与当前工作 | B 完成可信结果与继续，C 在 overview 显示当前工作、待处理、最新交付和下一步；不需要先搬完整工具循环 |

上表是后续设计建议。OpenAgentX 的完整自主跨领域委派并未由此前评估证明交付，本批也没有新增实现；Holon 对照不能补足这项验收。
