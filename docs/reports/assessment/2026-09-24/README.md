# OpenHarness 与 Wake 对照研究

## 结论

- **两个项目都值得参考，但解决的问题不同。** OpenHarness 帮用户组织、观察多个机器上的 Agent；Wake 帮用户找回已有会话、定位内容并交给原工具继续。它们分别补充执行工作台与历史入口的设计参考。
- **OpenHarness 最值得借鉴的是明确的结果提交、产物归属和恢复反馈。** 其编排器不会把空闲当成成功，未知启动也不自动重跑；但显式 `finish` 与文件哈希仍不证明业务正确，编排取消标记也不证明进程已经停止。
- **Wake 最值得借鉴的是围绕“找到并继续”组织界面。** 稳定引用、索引新鲜度、按能力显示恢复入口，都适合改善 OpenAgentX 的结果定位和 overview；外部终端打开成功不等于模型已经恢复或工作已完成。
- **不增加第二套执行或状态体系。** OpenAgentX 应继续使用 Task / RunAttempt / Journal / Worker 的权威链路；借鉴交互和验收方法，暂缓引入全量会话扫描、跨机镜像、原生桌面、Relay、Harness 市场与多层编排。
- **本批只有固定源码研究与隔离局部测试。** 没有运行两个项目的完整客户端、真实模型、跨机通信或桌面恢复，也没有重跑 OpenAgentX 的真实 Runtime / 浏览器验收；不能据此评定整体体验优劣。

## 比较方法

- 先确定项目实际解决的问题，再与OpenAgentX比较；不把Agent SDK、个人会话工具和组织任务控制面默认当同类替代品。
- 区分源码存在、fixture/fake测试、真实Provider和用户效果证据；测试名包含E2E不自动提升证据级别。
- 借鉴以减少核心流程断点为目标，保留OpenAgentX事务、Mailbox、Journal、lease/fencing和未知副作用不自动重跑的边界。

## 四个项目如何分工参考

下表只比较已读固定源码和报告证据，不是性能或产品成熟度排名。前两份研究保留原日期，不把其测试计入本批。

| 项目与报告 | 主要服务的用户动作 | 对 OpenAgentX 的高价值参考 | 本阶段不迁入 |
|---|---|---|---|
| [Paseo](../2026-09-23/07-paseo-reference.md) · `4c05138` | 创建会话、发送、审批、看本轮结果、继续 | turn 结果归属、继续入口、取消作用域、重连后补权威历史 | idle 代替业务成功；完整 native / relay / 插件栈 |
| [Multica](../2026-09-23/08-multica-reference.md) · `90e0bdf` | 连接计算机、创建 Agent、分派任务、看回复 | 角色真正传入 Runtime、任务/执行/会话分层、结果与续接指针 | 默认自动审批、未知副作用自动重试、完整团队治理；许可证含附加条件 |
| [OpenHarness](09-openharness-reference.md) · `a53351b` | 观察和操控多机器 Agent、编排任务并交付产物 | 明确 finish、attempt 归属、产物快照、投递未知时停止盲重发 | tmux 执行权模型、全套 Harness / Studio / Relay；取消状态替代停止确认 |
| [Wake](10-wake-reference.md) · `269c50b` | 找到旧会话、搜索定位、阅读、打开原工具继续 | 历史导航、稳定引用、能力说明、空索引与过期索引提示 | 扫描全部 Provider 私有文件、独立索引成为业务权威、SSH 镜像和桌面重写 |

四个项目共同提示的改进是：让用户随时知道“当前在哪一步、结果在哪、下一步能做什么”。这不需要把它们各自的完整后端并入 OpenAgentX。OpenHarness 和 Wake 的仓库根许可证均为 MIT；若后续复制具体实现，仍需保留版权与许可并核对该部分依赖，本批没有移入第三方产品代码。

## 沿用现有 A / B / C，控制改动总量

本表是后续实施建议，不是本批已完成能力。优先级沿用[总体评估第 8 节](../2026-09-23/00-overall-assessment.md)，不因新发现的参考实现而回开全量重构。

| 顺序 | 最小用户结果与参考 | 最小实现边界 | 后续验收 |
|---|---|---|---|
| A：可靠撤回与结果 | 未执行任务可撤回；多轮始终看到最新结果。参考 Paseo 的归属、OpenHarness Pause 的同目标停止确认及编排取消反例、Wake 的定位入口 | 修现有取消事务和当前 Run 投影；中断未确认仍显示未知 | queued / waiting_input 取消后不执行；活动取消失联不误报停止；不同轮回复定位正确，同 Worker 可继续下一任务 |
| B：真正完成一项工作 | 角色有效、query 能结束、action 有验证依据、接受的补充有去向。参考 Multica 的输入接线和 OpenHarness 的显式结果 | 对齐已有 ADR-006 intent / verification；按任务实际需要记录结果与可核验产物；继续仍走正式 Control API | 真浏览器→正式 Worker / Runtime→回复或文件效果→继续；联合核对 Task、RunAttempt、Journal 与实际内容，不用文件哈希替代业务断言 |
| C：从零到日用 | overview 可导航、未就绪能修复、历史能找回。主要参考 Wake，结合 Paseo / Multica 的恢复提示 | 先用现有查询投影展示就绪、待处理、最近结果与下一步；必要时补 API，保持 Web / Console 同一语义 | 无预置网络的新用户完成首项任务；首次连接失败可恢复而不重复提交；80×24 和 390px 下能到达结果与继续入口 |

只有当单机默认流程通过上述真实验收，且实际用户出现大量历史检索、跨 Provider 或多机器需求时，才重新评估 FTS / MCP / SSH 镜像或新的远程执行支持。此时也先做正式 API 上的只读查询，避免用外部会话文件推断 Task 成败。
