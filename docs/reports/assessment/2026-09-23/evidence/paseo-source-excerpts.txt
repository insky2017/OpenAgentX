1: # Product
2: 
3: Paseo is an environment for running, monitoring, and interacting with coding agents across desktop, mobile, web, and the command line.
4: 
5: **Paseo has a lean, opinionated core built to be extended.** It should be easy to start using and leave room for people to build far beyond the default experience.
6: 
7: ## Agents are the focus
8: 
9: The central workflow is giving an agent a task, understanding what it is doing, providing direction, and reviewing the result. Files, terminals, diffs, and other supporting tools help you do that.
10: 
11: Paseo should make this workflow coherent across providers and devices. You should be able to use the agent that fits a task and keep working from another device without rebuilding your environment around it.
12: 
13: This is the basis for product decisions. A familiar feature from another development tool earns its place by improving that experience. Familiarity alone does not make it a requirement for Paseo.
14: 
15: ## A low floor and a high ceiling
16: 
17: ### Easy to start
18: 
19: The default experience should be lean, polished, and understandable to someone who has never run a server or configured a VPN.
20: 
21: With a supported coding agent installed and authenticated, you can open the desktop app and start working. The app manages its local daemon. To connect your phone through the optional Paseo relay, enable pairing and scan a QR code. You do not need to configure a VPN or understand the networking behind it.
22: 
23: You should not need to know that plugins exist to get a useful, complete experience. Extra capability should become discoverable when it helps with something you want to do.
24: 
25: Keeping this starting point approachable is an ongoing responsibility. A technically correct feature can still make the product harder to understand through extra choices, controls, or setup.
26: 
27: ### Room to build your own setup
28: 
29: The same product should also work for someone running agents on a home server, using their own network, or building an automated workflow.

1: # Agent lifecycle
2: 
3: How an agent is created, runs, becomes a subagent, gets archived, and disappears from the UI. The model spans the daemon (lifecycle, archive) and the client (tabs, the subagents track).
4: 
5: ## States
6: 
7: ```
8: initializing → idle → running → idle (or error → closed)
9:                  ↑        │
10:                  └────────┘  (agent completes a turn, awaits next prompt)
11: ```
12: 
13: Each live agent in `AgentManager` carries a `lastStatus` of `initializing`, `idle`, `running`, or `error`. `closed` is the persisted, resumable state for an agent record that has no live provider runtime. State transitions persist to disk and stream to subscribed clients via WebSocket.
14: 
15: ## Runtime residency
16: 
17: An unarchived agent may be `closed` without being deleted or archived. Closing releases its provider
18: processes and subscriptions while retaining its Paseo identity, persistence handle, timeline,
19: workspace, labels, title, usage, attention, timestamps, and parent relationship. Opening or prompting
20: the agent runs through `ensureAgentLoaded()`, which resumes the durable provider session under the
21: same Paseo agent ID. Provider history is not appended again when the canonical timeline is already
22: primed.
23: 
24: Reload releases the old runtime before resuming its durable session: an idle provider process can
25: still own an exclusive writer. A close failure retains that runtime for cleanup and blocks the
26: replacement. Once closure succeeds, a failed resume leaves the durable agent closed and retryable.
27: 
28: Idle agents remain resident indefinitely. Runtime closure happens only through an explicit lifecycle
29: action such as archive, replacement, reload, workspace teardown, or daemon shutdown.
30: 
31: A provider runtime can still die on its own — crash, OOM kill, host suspend. Work the agent parked
32: inside that process dies with it: Claude Code's background Bash shells, `Monitor` watches, and
33: workflows all live in the CLI process, and the completion notification that would have woken the
34: agent never arrives. A runtime that dies mid-turn is reported by whatever is draining its stream, but
35: between turns nothing is watching, so the agent sits at `idle` looking healthy while its background
36: work is gone. Report that exit as a turn failure so the agent lands in `error` with a timeline entry.
37: Only the Claude provider does this today; the others still report a death only when a turn happens to
38: be in flight.
39: 
40: ### Cancellation
41: 
42: Provider interruption is idempotent at the `AgentSession` boundary. It resolves when the prior
43: foreground turn can no longer run, including when the provider reports that it is already idle. It
44: rejects only when the provider may still own the turn. Provider adapters translate native errors
45: into that contract; lifecycle callers do not interpret provider-specific errors.
46: 
47: After an acknowledged interrupt, the manager settles the captured run even when no terminal event
48: arrives or the run was still waiting for its provider turn id. The captured run token prevents an
49: older cancellation from settling a newer turn. If interruption is rejected or times out, the agent
50: keeps its active foreground turn and replacement, reload, rewind, and Stop report the failure.
51: Accepting new work after an ambiguous interruption would create a split-brain session.

1: # Daemon permissions
2: 
3: The daemon authorizes principals with semantic permissions. RPC names and protocol namespaces are not authority.
4: 
5: ## Model
6: 
7: ```text
8: principal -> grants
9:     |
10:     +-- authenticated by a device or service credential
11:     `-- opens a session with equal or narrower authority
12: ```
13: 
14: A principal is the durable identity the daemon authorizes. A credential proves that a device or service represents it. Keep them separate so you can rotate credentials, attach more than one device, and revoke a Hub user without inventing daemon user accounts.
15: 
16: A pairing invitation is neither. It is an expiring, single-use exchange that creates a principal and credential with the permissions selected by its issuer.
17: 
18: ## Permissions
19: 
20: | Permission          | Authority                                                                  |
21: | ------------------- | -------------------------------------------------------------------------- |
22: | `daemon.read`       | Daemon status, diagnostics, configuration, and provider information        |
23: | `daemon.manage`     | Restart, update, configuration changes, providers, skills, and plugins     |
24: | `tunnel.manage`     | Relay, Hub, service tunnel, and public endpoint relationships              |
25: | `access.manage`     | Pairing invitations, principals, credentials, grants, and revocation       |
26: | `workspace.read`    | Projects, workspaces, agents, timelines, files, diffs, and terminal output |
27: | `workspace.write`   | Prompts, agent control, files, terminals, git operations, and scripts      |
28: | `workspace.manage`  | Create, rename, archive, and remove projects and workspaces                |
29: | `automation.manage` | Schedules, heartbeats, and loops                                           |
30: | `hub.execute`       | Agent lifecycle, agent/workspace observation, and workspace recovery       |
31: 
32: Agents and terminals use workspace authority. Both can execute code and mutate the workspace, so separate write permissions would claim an isolation boundary the daemon cannot enforce.
33: 
34: Owner, operator, and viewer are UI presets expanded into explicit permissions. Do not persist them as roles. Adding a permission must not silently widen an existing principal.
35: 
36: Permissions are additive allows. Missing authority denies the operation. Do not add deny precedence.
37: 
38: ## Resources
39: 
40: Permissions are daemon-wide today. Future grants may select workspaces or agents, but operation classification remains inside the authorization module:
41: 
42: ```ts
43: type Grant = {
44:   permission: Permission;
45:   resource: { kind: "daemon" } | { kind: "workspace"; ids: string[] };
46: };
47: ```
48: 
49: A delegating principal can grant only authority it already possesses. A session may attenuate its principal's grants but cannot widen them.
50: 
51: Workspace-scoped grants require every resource-bearing operation and outbound observation to enforce the same workspace boundary. File preview currently accepts any daemon-readable regular file, so it must gain resource enforcement before workspace-specific access ships.
52: 
53: ## Hub
54: 
55: The Hub authenticates as a service principal. Its locally selected grants decide whether it may execute agents, manage the daemon, manage tunnels, or manage access.
56: 
57: Hub user and role identifiers remain opaque external subjects. The Hub may create and revoke linked daemon principals when granted `access.manage`; the daemon does not interpret accounts, organizations, or roles.
58: 
59: Hub enrollment and permission updates exchange these semantic permissions directly. Legacy persisted Hub relationships that contain `hub.execution.*` migrate once to `hub.execute` when the daemon loads them; new relationships never persist or emit transport scopes as authority.

FILE docs/timeline-sync.md L1-22
1: # Timeline sync
2: 
3: Agent chat delivery has two paths:
4: 
5: 1. **Live stream** — `agent_stream` WebSocket messages for immediacy. These may be delta-shaped lifecycle updates.
6: 2. **Authoritative history** — `fetch_agent_timeline_request` for correctness. This always returns full projected timeline items, never lifecycle deltas.
7: 
8: The daemon retains projected items in memory. Each source event advances the stream sequence,
9: then replaces the previous tool state or merges into the current text item. Intermediate payloads
10: are never retained for history or catch-up. Provider history is the durable transcript authority
11: and rebuilds the projection when an agent resumes.
12: 
13: The invariants are:
14: 
15: > A continuously subscribed client applies every committed row in order. Opening or resuming an
16: > agent establishes the daemon's current tail in one bounded request, with older history reachable
17: > through backward pagination.
18: 
19: Tool output is bounded before it enters either delivery path. Canonical shell tool output is sliced
20: to 64 KiB, and the same bounded item is used for runtime timeline rows and live stream events.
21: Provider history hydration applies the same rule so reopening an agent cannot restore an oversized
22: tool payload.
