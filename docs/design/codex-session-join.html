02

先选你的会话处于哪种情况

“Codex 会话”保存聊天历史；“OAX Agent”保存长期名字、目录和职责。加入 OAX，就是为这个领域建立身份，并决定由哪个入口继续执行。下面的按钮只切换说明，不执行任何接入操作。

推荐 · 没有旧历史要迁移时最短

直接创建一个由 OAX 管理的 Codex Agent

你只需确定名字、工程目录、职责与希望协作的对象。先创建并打开终端，再把这个新领域加入协作目录。

  1. 用现有命令创建身份和后台

    agent add --runtime codex 已实现；可直接用 --role-text 给出职责，不必先手工写 ROLE 文件。

  2. 打开原生终端，等待自动初始化成功

    首次没有会话时，open --native 会调用模型执行一个初始化 query Task；成功后显示终端，不用你再手动发一句初始化。核对实际 thread / Task 绑定，服务 online 本身还不足够。

  3. 由管理侧启用与指定领域的协作

    合并职责目录、配置双方通信许可，再做一次只读咨询与自动续办验证。具体见第 04 节。

查看当前可用命令：以 research 作为新身份示例

先替换示例名字、目录和职责，确认 ID 未被占用。首次登记可能需要本地 owner 登录；私密密码文件可由管理侧传入 --password-file。

openagentx agent add --runtime codex --id research --name Research \
  --workspace /absolute/project \
  --role-text '负责本工程研究与实现；支付及其他领域事项向对应负责人咨询。' \
  --no-open

openagentx agent status research
openagentx agent open research --native
最后一条在交互式终端运行；启动的是当前终端中的原生界面。

若要固定到 OAX:research.0，还需要定向安排 Fleet 窗口；上面的 open --native 不会自动替你创建固定窗口。不要用全量 fleet up 随手启动其它 Agent。

这里不需要先运行裸 codex 再迁移。你仍然在官方 Codex 终端里工作，后台执行由 OAX 管理。首次 open 会产生真实模型执行，不能当作只读查看命令。
可用 · 分准备与接管两段

让正在工作的 Agent 自己准备，然后交接

  1. 在当前会话单独输入短入口

    已发现该 Skill 时，一行就可开始；它先利用已有上下文，只补问缺失的身份、职责或协作对象，不启动后台抢占自己。

  2. 结束本轮，并退出旧 Codex 执行入口

    希望保留历史时，用有明确来源的 thread ID。仅显示 idle 不代表会话已释放；管理侧需要核对后再接管。

  3. 管理侧 resume → 原生终端 → 协作验证

    同一个 Agent 继续用原目录和职责。没有可靠 thread ID 时，只能交接摘要并新建历史，须明确告诉你。

直接复制给当前 Agent · 无需另写启动句
$oax-join

长名 $openagentx-join 继续兼容。当前会话尚未发现短名时，先查看安装与自检说明；不要把“Skill 可见”当作已经接管。准备回执为 local_prepared / ready=false，不会自动 resume、切换执行入口或发协作消息。

准备完成后，管理侧执行什么？

下面使用 research 示例。必须先核对旧入口已释放；默认代理沿用现有私密环境或接入时发现的本机代理，不要求重新配一套。

openagentx agent resume research --no-open
openagentx agent status research
openagentx agent open research --native

resume 启动并检查后台；原生入口建立实际会话，成功绑定之后才可启用 managed 协作。遇到 writer 冲突或结果未知，先核对原进程和 Task，不删锁或盲目重试。

先决定日后在哪个入口工作

Desktop 可以保留作历史查看，自动协作走 OAX 终端

要继续在 Desktop 执行

可登记 external 身份，用 oax-collaborate 在被用户唤起时收发消息。

当前未打通可靠的事件自动唤醒。收到消息后不会保证这个 Desktop 会话自动执行，Skill 不能补上宿主接口。

要空闲后自动协作

推荐把执行入口迁到 OAX 托管终端，明确保留原 thread；原 Desktop 只读历史。

Rhythm / Pay 已走通这一方式。交接过程需要核对旧宿主释放，不能让两个入口同时操作同一会话。

  1. 给出 Desktop thread ID，准备身份与交接

    采用与“已有终端会话”相同的 prepare 流程；ID 从可靠会话信息获得。

  2. 管理侧核对并释放原会话

    停止 turn 不等于释放 writer。此前 Rhythm 曾需要正式归档 / 取消归档并核验 notLoaded；该操作可能影响子任务，不能直接做成通用的一键归档脚本。

  3. 定向启动 OAX 终端并验证原历史

    确认 thread、工作目录、职责和目标窗口，再开启协作。原历史保留与首次自动往返分别验证。

如果这个 Desktop session 刚创建、还没有重要历史，最省事的是走“还没开始的新工作”路线，只交接简短需求，创建新的 OAX 会话。

查看 Rhythm / Pay 的真实切换经过与限制

这个会话已经用 external 方式登记过，怎么办？

这时不能当全新身份重复创建。管理侧先读取当前绑定与 generation，处理未完成请求、任务和未 ACK 结果；经确认后撤销旧 external 绑定，再按最新 generation 启用 managed，保留同一原 thread。撤销通信凭据并不会释放 Desktop writer，仍需单独核对原宿主。

当前还没有把这些交接步骤全部封装进 join Skill；可参考已完成的原身份切换实录。页中所有 research 命令都是新身份示例，不应套用到已启用身份。

04

怎样确认真的接通了？

不要只看一句“已加入”。最终应能告诉你：这个身份是谁、从哪里工作、可以问谁，以及是否真的完成过一次自动往返。

阶段看到什么才算完成目前由谁完成
身份已准备ID、目录、职责、交接摘要；回执为 local_prepared / ready=false。现有 join Skill + prepare helper，已实现。
可以开始工作后台与网络就绪；原生终端可对话；实际 Task 与 thread 对应正确。管理侧 resume + 原生入口核验。已实现。
协作已配置职责目录包含本域；双方通信许可正确；managed 绑定基于真实 SessionBinding。管理侧配置 roles / peers / enable。现有 join Skill 未串联。
自动协作已验证真实咨询到达对方 → 对方回复 → 本域自动读入续办。保存消息、Task/Run/Journal 与答案。已有真实案例；每个新接入应做自己的小验收，不能借用其它 Agent 的成功。
为什么职责与通信对象还要配置一次？管理侧怎样做？

ROLE 告诉模型“我负责什么”；组织职责目录告诉消息系统“这类问题该找谁”；peer 列表决定“谁能和谁通信”。这三者现在是分开的，所以仅写 ROLE 不能获得自动协作。

现有命令为 openagentx collaborate roles --owner --organization default、openagentx collaborate roles apply --file /absolute/roles.json --expected-version <实际revision> 和 openagentx collaborate enable --agent … --peers …（自定义组织需替换 default）。先读取现有目录和绑定，合并新增领域；双方 peer 都要核对，已有绑定使用现场 generation。不能用示例覆盖已有 Rhythm / Pay 规则，也不能硬编码代次。

enable 前必须已有真实会话绑定；成功后让 Agent 读取 openagentx collaborate instructions --agent <自身ID>。此处是 managed 协议：正常最终答复由后台关联发送，不再套用 external Skill 的手动 reply 步骤。完整命令与约束。

注意：旧接入指南关于“resume 失败必保持 Fleet 禁用”的表述与现有 prepare→resume 代码不完全一致。本页以实际 status、Task 与绑定结果判断接通，不能仅凭 Fleet enabled。差异已列入本轮核查记录，未在分析任务中修改产品逻辑。

你日常应该只记住一个入口

进入属于该领域的原生终端，继续布置本域工作。其他领域的问题由它咨询，后台在有任务时执行。

固定窗口需要单独核对，例如 OAX:research.0。名称、工作目录与 thread 都正确后，日常不必再处理 Fleet、token 或服务细节。

当前自动协作能做什么

支持只读咨询、答复和请求方自动续办；忙时持久排队，关闭前台不会关闭 Worker。

这不等于可自动接受任何跨域修改请求。部署、支付操作、数据迁移仍按你的明确任务授权执行。

Skill 应该安装在哪里？为什么现在没有直接出现？

本轮核对的官方文档将用户级位置写为 ~/.agents/skills，工程级位置为从当前目录到仓库根的 .agents/skills，支持符号链接；Codex CLI 可通过 /skills 或 $ 选择。当前 Desktop 会话还列出了既有 ~/.codex/skills/oax-collaborate，两者不能仅凭目录名称视作同一发现结果。

此前长名 ~/.agents/skills/openagentx-join 已通过真实可见性检查。本批新增 oax-join 为首选短入口，保留长名兼容；隔离真实模型已验证只输入短名即可完成准备。安装后的真实 skills/list 已确认两个同源入口均为 visible / enabled，详见本批交付记录。安装器不会覆盖不同来源；check 只验证独立新进程发现，不保证当前已运行 turn 自动注入。安装与自检命令。

官方 Skills 文档（本轮已读取）。官方说明支持自动发现变更；若未出现，再重启该 Codex 入口。不同宿主以实际显示为准。

本次建议的优先选择：新的领域直接创建托管 Codex；已有重要历史先 prepare，再核验交接。下一步实施只需提供：稳定名字、工程目录、职责及协作对象；已有会话再提供 thread ID，并决定是否保留历史。
