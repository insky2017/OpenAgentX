01

希望最终怎么用

RESPONSIBILITY / 职责

原领域继续负责

Rhythm、Pay 各自登记职责，分别推进应用与支付开发；需要配合时按 scope 咨询和回话，用户不再复制消息、来回传话。

CONTINUITY / 连续

一轮结束，仍能接下一单

后台程序常驻等待。有工作才启动模型；忙时排队，等待用户或审批时保留当前状态。

VISIBILITY / 可控

固定入口，少操作

用户进入同一个 OAX session，即可找到各 Agent 的终端、看执行过程并输入；每一步留证据、逐关确认。

用真实场景核对：Rhythm 接入订阅支付时，我希望系统怎样工作
  1. Rhythm 继续应用开发，需要确认支付接口时，向 Pay 发一条有明确问题与证据的咨询，用户不再转述正文。
  2. Pay 忙时消息排队；空闲后处理自己的接口、回调协议与支付记录，超出 Pay 的用户映射、权益或应用部署问题明确交还 Rhythm。
  3. Pay 的关联答复持久保存；Rhythm 当前轮结束后自动读入答复，再继续自己的接入工作。等待答复期间由程序保存状态，不让模型一直运行 watch 等消息。
  4. 你在 OAX:rhythm.0 与当前 Pay 入口 OAX:pay-service.0 查看各自过程、输入新要求；系统协调同一 Agent 的输入顺序，不影响另一个 Agent 并行开发。
  5. 已读、接单、回复与实际业务完成分别可查。首次试点只读咨询，不因通信成功就支付、退款、改回调或部署。

本轮已用这两个原业务身份完成真实只读咨询闭环；图中的 Rhythm / Pay 已对应实际托管进程。收费接入本身仍是后续业务任务。

02

事件触发：有人交来工作，才让 Codex 开始一轮

没有新工作时，普通后台程序等消息。有工作时，先记下来，再交给空闲的执行程序。等待期间不需要模型反复回答“有没有新消息”。

你会得到什么

没有任务时不产生空醒模型请求；Pay 发来答复后，Rhythm 能被安排继续工作；你仍可从终端看到过程、输入新要求。原 Rhythm / Pay 的自动往返已实测；此前独立测试的 30 分钟空闲窗口新增 Task、模型轮与工具调用均为 0。

哪些事情还要单独处理

真正干活的一轮仍有上下文费用。消息收到、任务执行完、业务结果正确，也是不同的状态；事件触发本身不能替代业务验收。

external inbox --watch 到底是什么？

它是一个持续打开的收件箱查看器。例如在普通终端中运行：

openagentx external inbox --agent rhythm --watch

这条命令每 2 秒向本机 OAX 查询一次 Rhythm 的外部协作收件箱，有新消息就打印出来。它不调用模型，也不会替你回复、确认收件或启动 Codex 的下一轮；按 Ctrl-C 就退出。

所以，“查看到消息”和“让 Agent 处理消息”之间还差一个执行衔接。这个查看器不在第 05 节已经实现的托管任务主链中；后台 Worker 领取的是自己的任务待办。

03

为什么原 Desktop 还不能承诺自动接单

工具与 Skill 能告诉正在执行的 Agent 如何收信、回复和恢复，不能自行唤醒已经结束的模型轮。原 Desktop 可靠的事件入站、忙时排队、人工输入竞争及审批等待路径，当前没有完整实测证据。

原生 heartbeat 曾成功触发原 thread，但没有形成新的收信与协作闭环。因此不能把“界面里出现回答”当作自动执行成功。

共享 app-server 确有 thread/queue/add、thread/queue/start 协议，但历史探测中两个目标 thread 在该 daemon 显示 notLoaded；原 Desktop 由独立 stdio app-server 持有。缺的是当前接入方式下正确宿主的可靠入口，不是 Codex 没有队列，也不是 Desktop 永远无法自动化。

为什么自动消息不直接粘贴进 pane 0？

tmux send-keys 相当于替你敲键盘。比如你正在输入“先检查接口……”，程序这时把一封咨询也打进输入框，两段文字就可能混在一起。CLI 正忙时，这段输入是修改当前工作还是排到下一轮，也取决于当时的界面状态。

当前采用的处理方式是：你照常使用终端，自动消息通过后台登记成任务。这样能分别知道哪条任务来自你、哪条来自其他 Agent，以及各自是否已经接下。第 05 节的连接器负责把你的新任务也登记到同一 Agent 的待办中。

具体连的是什么？Task / Mailbox 又在哪里？

TUI 与 Bridge、Bridge 与 app-server 都通过 WebSocket 交换结构化 RPC 消息；当前底层使用本机 Unix socket。传输的是带 id / method / params / result 的请求、响应与事件，不是往终端输入框注入按键。

Task / Mailbox 是 OAX 的 SQLite 数据。Task 保存任务正文、目标 Agent 与状态，Mailbox 保存该 Agent 的待办与领取情况。Worker 领取的是已经指定给自己的工作，不再选择目标 Agent。

现有桥接只支持 Codex 和部分接口：输入限文字，未列入白名单的操作不透传，审批由后台处理。已验 Codex 版本为 0.160.0，其 app-server 标为实验性；这不等于所有 Codex 原生功能或其他 CLI 都已接通。

05-C同一后台，两条事件连接：一条给你看，一条留下执行记录

app-server 主动推送事件；Bridge 和 Worker 分别接收。Worker 进程内部的 Codex Adapter 负责理解 Codex 协议，筛选当前 thread / turn 的事件，再调用 Worker 提供的上报函数。OAX 服务收到上报后写入数据库。

只演示连接关系，不操作真实终端

终端打开：Bridge 的连接 A 显示实时过程；Worker 的连接 B 独立接收执行事件并上报。两条连接观察同一个 Codex 会话，不会因此执行两次任务。

保存的是经过处理的执行记录。当前 Adapter 把完成项转换为输出事件，并收集最终答复、用量与结束状态。屏幕上的逐字输出不逐条写入 Journal；因此“终端看到全过程”和“数据库完整保存所有原始事件”是不同能力，后者当前没有实现。

接口级细节：Subscribe、EventSink、上报 API 分别是什么？
  1. 建立连接：Worker 的 Adapter 与 Bridge 各自使用 DialRPC(endpoint) 建立 WebSocket 连接，通过 thread/resume 关联同一 thread。连接收到 app-server 的推送。
  2. 程序内分发：每个 RPCClient 的 readLoop 读取消息；请求结果交回调用者，通知和服务端请求发给本地 Subscribe() 返回的 Go channel。Subscribe() 不是另一个叫这个名字的 Codex 网络接口。
  3. Worker 上报：Adapter 调用 EventSink.Emit，这是 Worker 提供的函数回调；回调调用 AppendRunEvents，发往 POST /api/v1/run-attempts/{run-id}/events。
  4. OAX 保存：服务校验 Worker 身份、执行版本与有效租约，把允许公开的事件投影为 runtime.* Journal 记录，通过 SQLite 事务保存。轮次结束另走 POST /api/v1/run-attempts/{run-id}/finish。

Bridge 只向 TUI 转发当前 thread 的通知；带 ID 的服务端请求（例如审批）由后台处理。两条连接承担不同职责，没有“Bridge 先收齐事件再交给 Worker”的依赖。

05-D协作消息到任务：收信后自动处理，再通知对方继续

消息与正式任务已接通：咨询保存与目标待办同时落库；任务结算与关联答复同时落库；请求方为 managed 时自动建立只读续办。下图紫色虚线表示已实现的协作路径。消费答复结束后不会再自动回信。

现有消息 API 有目标身份与职责检查；当前 external 身份与 managed 托管身份互斥。当前已有模式接入、职责校验与消息／任务关联；失败、绑定或职责变化会进入 needs_review，不盲目重做。两原业务身份现均为 managed / active，并保留原 thread。

完整答复与过程摘要分开保存。当前最终答复可保留至 32 KiB，事件和错误摘要仍为 4 KiB；本次 Pay 的 7,973 字节答复已完整传到 Rhythm。真正超过答复上限时保留需核对状态，不用截短结果冒充成功。咨询只要求对方提供领域事实，后续业务修改仍按用户任务执行。

同一条消息重试时，为什么还要保存处理记录？

例如 M17 已保存但发件人没收到确认，可能重发；收件程序重启也可能重新读到 M17。衔接程序要查到它已有对应任务，继续原工作。它不把这次重读当成第二项新工作。你主动发出的两次新请求仍可分别执行。

  • 真实原生终端验收：输入、执行、退出后继续、重开历史。这是历史单 Agent 证据；此前独立托管验收另含双 Agent 与 PTY 断开复验，本轮原身份迁入见第 09 节。
