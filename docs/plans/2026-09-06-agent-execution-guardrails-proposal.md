- 根因分析主参考：[Gemini 执行复盘](../reports/validation/2026-09-06-openagentx-adr002-003-execution-retrospective-gemini.md)。
- 时间与用量事实附件：[原执行记录与统计](../reports/validation/2026-09-06-openagentx-execution-retrospective.md)。

## 根因与本次修正

- 核心失误是目标置换：逐渐把消除审核意见、补齐证明材料当成完成目标，用户何时能用上功能失去优先级。
- 主代理没有行使工程裁决权。审核提出可能风险后，未经当前部署条件、真实影响和修复成本判断，就转交实现并回开验收。
- 理论边缘场景进入当前交付，增加防御代码与测试；脆弱验证工具又制造新问题，推动环境重建、再次派发和重复审核。
- 多代理传话、长文档和重复上下文扩大成本；按代理角色统计 token 只能说明消耗来源，不能证明这些工作值得做。
- 前版把大量篇幅放在监督程序、隔离环境和模型网关建设上，没有先纠正上述决策。硬限额能够止损，但不能替主代理判断一个问题是否值得当前处理。

本次调整的核心是：主代理对每个新增阻断项的现实影响、必要性和成本负责，以当前交付条件是否满足决定下一步。监督程序和预算限制作为止损措施，不成为交付功能的新前置项目。

## 主代理必须作出的裁决

审核意见是裁决输入。`P1`、`NO-GO` 等标签不能自动触发开发和整轮回归；主代理必须先确认它是否直接破坏当前验收。

每项拟进入当前批次的新增问题，用一条简短记录回答：

| 必答项 | 需要说明的事实 |
|---|---|
| 当前影响 | 影响哪条用户主流程或已冻结验收项；触发条件是否存在于当前部署与支持范围 |
| 证据 | 可复现失败，或足以确认问题的源码/契约证据；不能只列一种理论可能 |
| 不修后果 | 是主流程失败、崩溃、直接安全风险、数据破坏/重复执行、虚报成功，还是后续完善 |
| 最小修法与成本 | 修到当前要求成立所需的最小变更及验证；有无更小且符合契约的处理方式 |
| 裁决 | 当前修复、后续处理或有界诊断；由主代理负责，不继续无期限转发讨论 |

具体执行原则：

- 能证明上述直接风险的问题阻断当前交付；即使难修，也不能靠降低严重性或虚报通过来收口。
- 理论上可能存在但与当前部署、支持范围和验收无直接关系的问题，记录后续处理。需要补事实时安排一次有界诊断，不能无限推演。
- 高风险影响尚不能确认时，暂停相关操作并报告未知点；不把缺少证据解释为安全，也不默认启动全面加固。
- 只有范围或预算需要超出用户现有授权时才请求变更。常规实现取舍由主代理负责，不把裁决责任反复交回用户。
- 已完成的改动保留，不因复盘认定投入过度就自行回退；也不因已经投入大量成本而继续扩大任务。

## 复杂度必须匹配当前需要

以下例子用于说明裁决方式，不构成修改现有代码或收窄既有契约的授权：

| 需求 | 当前应判断什么 | 需要额外依据才能扩大到的工作 |
|---|---|---|
| 控制台网络配置 | 页面配置是否持久化、正确应用到目标 Worker，新任务是否实际使用该版本 | 底层库全面研究、脱离当前威胁模型的目录防御及完整文件回收体系 |
| 任务列表分页 | 当前支持的时间和数据范围内是否稳定、完整，游标是否正确 | 极端年份编码、自定义数据库驱动或通用时间体系重构 |
| Markdown 与观察 | 标准组件能否安全展示真实内容，必要交互与结果来源是否清楚 | 为观察页面建设完整的通用业务副作用核验体系 |
| 真实任务验收 | 平台是否正确运行和报告，业务输出是否符合要求 | 为消除一次业务失败而不断追加模型任务，追求没有失败历史的报告 |

是否安全、是否成功仍须如实判断。模型任务失败与平台功能失败分别记录；不能将未知副作用报成成功，也不能让一次业务输出偏差自动升级为平台重构。

## 验证与多代理必须服务交付

- 开始前固定一张短验收表，覆盖用户主流程和直接风险，明确本轮排除项。已有授权和验收可以直接复用，不重新制造审批流程。
- 主代理裁决，实现者修改，验证者集中验证，审核者核对关键风险与证据。分工按已授权方式执行，同一批次只有一个主要实现者和一个独立验证者。
- 一个主要实现批次、一次独立验证，失败后一次集中修复和受影响项重跑；仍失败则交接具体阻断。审核中新增问题必须先经过前述裁决，不能自动再开一轮。
- 验证脚本自身连续两次同因失败，停止该路径，先核对正式 API、对象身份、进程和前置条件；必要时采用更短的真实浏览器操作。静态检查不能替代实际交互，夹具失败不能直接写成产品失败。
- 已验证证据按变更影响复用。当前批次满足验收后按既定提交规则交付，明确未覆盖项；后续完善不无限绑定在当前提交上。
- 派发仅传目标、相关文件/变更、验收和当前阻断；历史证据按需引用。活动协调摘要保持一页左右，过程文件建议上限为 500 行或 15 KB，以先达到者为准；超出后归档引用，不广播全部历史。
- 进度报告回答用户已能完成什么、当前只剩什么阻断、继续处理的代价。消息数、报告数、通过多少内部审核不作为交付进展指标。

上述批次和体积限制是讨论中的建议，不表示当前平台已强制执行。文档归档应保留历史事实与必要证据，不删除失败或复制敏感日志。

## 止损措施与能力边界

建议开始前明确本批总时间和 token 预算，包含全部代理、重试和收口。达到 80% 时收口，达到 100% 时停止；单一功能连续两小时未收敛时必须报告已完成项、阻断和消耗，重新裁决剩余工作，不能自动增加预算或删减验收要求。具体额度尚未设置，这些阈值均未部署。

| 止损项 | 优先复用的能力 | 边界 |
|---|---|---|
| 总时间 | 现有宿主或进程管理器设置限时 | 必须覆盖主代理、子代理及后台进程，并确认清理完成；只停止父进程不够 |
| 总额度 | 统一任务账目，限制累计代理启动次数、并发和重试 | 换代理、压缩上下文、恢复会话不重置额度；仅事后计量不能保证在途请求不超额 |
| 暂停 | 持久化停止状态，启动和续推入口检查 | 只有用户明确恢复才能解锁；自动续推不构成授权 |
| 有限阶段 | 固定实现、验证、集中修复和结束步骤 | 到期交接已有事实，不追加模型任务撰写更多收口报告 |

这些措施应优先使用现有能力。缺少完整监督器或精确计费网关，不应成为完成普通功能的新增前置条件；缺少硬限制时必须如实说明，采用短批次和明确检查点，不能声称强制保证已经存在。

### 真正硬限制成立的条件

- 策略和监督程序位于模型权限之外，任务账号不能修改预算、解除暂停或绕过入口。所有代理、工具和模型请求都须纳入对应控制。
- 仅增加 `AGENTS.md`、同账号监督脚本或只读配置文件，不足以证明上述隔离成立。讨论时的完全访问会话没有证据表明已具备该机制。
- Codex 的 `codex exec --json` 可输出事件和完成后的用量。它适合监控；精确 token 上限还需逐请求拦截、原子预留输入上界与最大输出、共享结算，并禁止绕过。不能控制这些条件时，仅承诺实际具备的时间限制和用量监控。
- 收口资源提前纳入预算。强制停止不能撤销已经发生的外部副作用；未确认结果保留未知，不自动重试或推断回滚成功。

若未来确需建设监督器或网关，应作为独立需求评估收益、成本与验收，不能用“防止过度工程”为理由自动启动新的过度工程。

## 如何判断改进有效

工程治理首先看实际决策和交付结果：

| 检查场景 | 有效表现 |
|---|---|
| 审核提出边缘风险 | 主代理依据当前影响作出裁决，后续项没有自动进入本批 |
| 发现真实主流程缺陷 | 保留阻断，集中做最小修复及相关验证，不顺带重构整个模块 |
| 验证脚本反复失败 | 停止原路径，查明前置或换用更短的真实验证，不持续补造复杂脚本 |
| 当前验收已满足 | 按既定规则提交，列出后续项，不继续追求消除全部审核意见 |
| 成本接近上限 | 能报告剩余工作的价值和代价，按约定收口或交接阻断，不再自行续期 |

若实际部署了硬限制，还须验证：超限后全部受控进程停止；暂停在重启和续推后仍有效；换代理不重置额度；并发派发不超配或重复启动；修改策略和绕过入口被拒绝。证据绑定任务 ID、源码版本和实际执行结果，不能靠模型自报通过。

上述机制检查尚未执行。工程裁决改进和硬限制验证分别记录，不用一项通过替代另一项。

## 后续建议

1. 在下一次获准执行的任务中，先采用简短验收、主代理逐项裁决和有限验证批次；以交付推进检验效果。
2. 复用已有预算、限时和停止能力；确实缺少且值得建设的强制控制另列任务，不阻塞普通功能交付。
3. 保留用量统计作为成本证据，同时记录导致新增工作的决定，才能判断消耗是否值得。当前不恢复原任务。
