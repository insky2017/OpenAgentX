# OpenAgentX 端到端测试用例：AGY 工作流

日期：2026-10-02。配套[修复计划](2026-10-02-agy-workflow-repair.md)。**本用例集已获执行授权；结果按执行日志逐项记录，表中预期不代表已经通过。** 历史测试只能说明其对应版本和环境，不能直接填作本轮通过。

## 要点

- 验收单位是“用户操作到实际结果”的完整路径，每个本轮承诺的功能都映射到用例。
- 唯一真实 Runtime 为 AGY，使用与安装配置一致的 `agy-graft`、模型、工作目录和网络环境；不接 WorkBuddy／CodeBuddy 做本轮验收。
- 确定性故障测试负责稳定复现竞态、损坏输出和断线；真实 AGY 负责证明模型、工具、角色输入及实际效果；真实安装测试负责证明用户拿到的版本能够工作。
- 所有写文件样例在专用目录运行，从文件系统独立取证；不能靠模型说“完成”、截图或进程退出码判断通过。
- 首次失败保留。修复后重验相关用例，最后运行最终候选的完整日用链，不循环开展无边界全量审计。

## 1. 三层证据与环境

| 标记 | 实际组成 | 能证明什么 |
|---|---|---|
| D：确定性集成／故障链 | 正式 API、临时 SQLite、真实 Worker；按用例使用现有 fake Runtime 或 AGY 协议可执行夹具；UI 用例连接真实后端 | 状态、事务、消息、竞态、恢复、解析及 UI 接线。不能写成真实 AGY E2E |
| R：真实 AGY 链 | 正式入口 → daemon → SQLite → 常驻 Worker → 正式 AGY wrapper/CLI → 文件或回复 → 页面／Console | 本轮真实模型与工具效果，以及 Runtime 到产品的完整链路 |
| I：真实安装与交互 | 最终候选安装产物、真实 user-systemd、浏览器或 PTY/tmux、专用测试 Agent | 服务生命周期、实际版本、首次使用、回到工作台和安装后的日用体验；涉及模型时与 R 同时执行 |

执行前记录候选 commit、Go/Web 工件、AGY/wrapper 版本、schema 版本和配置来源。D/R 先用临时 profile、独立 DB/socket/端口及专用工作目录；I 使用唯一测试 Agent 和实际用户级 service。现有 Fleet 有 canonical binary/config 约束，不能仅替换 `OPENAGENTX_HOME` 就假定完成服务隔离；测试实例需按实际 unit 的 argv、配置与路径核对。崩溃、错误网络和损坏数据只注入隔离实例。

环境准备允许创建用户拥有的测试目录、安装候选并启动测试服务；不允许直接写 DB 伪造 ready、finish 或验收，不允许悄悄提前发布网络后声称“首次使用通过”。依赖真实 Provider 登录的步骤保留为明确环境前提；测试不打印或提交凭据。

首次网络探测成功只说明探测范围；首个真实 query 才证明本次模型调用成立。UI 必须区分 Worker 在线、网络已应用、最近模型调用结果及其时间。

## 3. 三条必须按步骤执行的样例

### 样例 A：全新 Agent → 真问答 → 同 Worker 第二项

覆盖 E01、E03、E04、E13、E22。

1. 准备空测试 profile 和 workspace；角色文档含本次随机标记，文件 `input.txt` 含另一个随机标记。角色标记不出现在用户问题中。
2. 用户通过向导添加 Agent，完成一次必要登录和网络选择。不得预置 binding 或手工修改数据库。
3. 打开 Web，选择“问答”，请求读取 `input.txt` 并按职责文档的格式回答。保存这次实际 Task/Run ID。
4. 核对输出同时反映文件内容和角色要求；核对持久 `FinalReply`、`query_result_delivered`、Task 状态、Journal 和实际运行 cwd。模型复述标记只是行为证据，还须有角色输入摘要/来源的接线证据。
5. 从 Console 发第二项不同问题；确认同一常驻 Worker 领取，显示第二项的结果。刷新 Web、退出再返回后仍正确。

失败示例：只有 Run 成功而 Task 仍 uncertain；第二项展示第一项结果；角色未注入；需要手动 restart Worker 才能继续；Token/密码出现在报告。

### 样例 B：写文件 → 验收 → 关联继续修改

覆盖 E05、E06、E16、E22。

1. 使用唯一工作目录和任务标记，选择“执行任务”。请求创建 `result.txt`，精确内容为 `OAX-E2E\n`，其中 `\n` 表示一个真实换行。
2. 等本次 Run 正常结束。测试进程独立读取文件，断言字节为 `b'OAX-E2E\n'`，记录大小和 SHA-256；检查文件在实际 Agent 工作目录中。
3. 页面展示结果和“待验收”。点击“接受结果”，核对正式 API 写入的 Task/Run/结果版本及人工验收来源；刷新后仍显示“用户已验收”。历史执行不确定记录不被篡改。
4. 再次提交相同验收请求，确认没有第二条有效验收或执行。对旧结果版本的验收不能被当作新结果的确认。
5. 继续输入“将上一文件增加第二行 `continued`”。应创建关联新 Task，携带明确文件引用及前项结果；独立断言最终字节为 `b'OAX-E2E\ncontinued\n'`，无重复附加。
6. 另一个子场景点击“结果有问题”：保存理由、可发起关联修订；不能自动重试旧任务或把拒绝当成接受。

**证明边界：** 独立文件检查证明该测试产物正确；用户验收记录证明有人接受该结果。二者都不能被概括为平台已经拥有任意业务副作用自动验证器。query 模式也不能被用来绕过这个差别。

### 样例 C：实际执行中取消 → 不再产生延迟效果 → 下一项

完整覆盖 E09，部分涉及 E10。E08 的排队／待输入撤回和 E17 的真实崩溃／重启须另按矩阵执行，不能用本样例替代。

1. 给测试任务一个可观察脚本：先写本次唯一 `started` 标记，再等待，最后拟写 `late.txt`。全部操作限于测试目录。
2. 从独立文件检查及实际进程证据确认等待已开始，再点击取消；不能仅按固定 sleep 猜测启动时刻。
3. 先看到“正在停止”。默认交互目标：本机点击后 1 秒内显示请求反馈；停止确认目标 5 秒内，实际阈值与正式 Adapter 清理预算一起固定。超时必须显示“停止未确认”，该成功取消子场景判失败，不能换成绿色通过。
4. 确认该任务的目标进程及后代已消失，超过原延迟窗口后 `late.txt` 仍不存在。`started` 已产生，不能宣传取消撤销了全部副作用。
5. 提交下一项 query，确认可以运行。另用 D 层控制取消/自然结束两种顺序及“请求已接受但 Worker 失联”，分别检查真实终态与未知状态，不自动重跑。

真实长任务另使用跨多个 lease 周期的等待；真实超时另用可配置短 deadline。它们验证控制面不会被工具静默阻塞，不以数小时压力测试作为首版前置。
